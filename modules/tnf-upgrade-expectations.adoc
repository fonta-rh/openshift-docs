= Cluster behavior during a TNF upgrade

[role="_abstract"]
A two-node OpenShift cluster with fencing (TNF) upgrades one control plane node at a time. The node that is not being updated keeps etcd quorum and the Pacemaker cluster running, so the upgrade completes without manual intervention. Short API interruptions and temporary cluster Operator conditions are expected and resolve on their own.

[IMPORTANT]
====
Start an upgrade only when both nodes are healthy. Do not start an upgrade while the cluster is degraded. For details, see "Prohibited operations during degraded TNF operation".
====

.Upgrade sequence

. The control plane Operators update first. This phase includes a new etcd static pod revision on both nodes, applied without rebooting either node.
. The Machine Config Operator (MCO) updates the control plane nodes one at a time. The MCO cordons and drains the node, applies the new operating system image, and reboots the node.
. Before the node shuts down, Pacemaker moves the fencing resources and the designated coordinator (DC) role to the other node. The other node keeps quorum, so fencing is not triggered.
. After the node boots, Pacemaker and the kubelet start on it. The TNF setup jobs in the `openshift-etcd` namespace run again: they briefly remove the node from the Pacemaker configuration, add it back, and reapply the fencing configuration. etcd then starts on the node and rejoins the cluster.
. When the node is `Ready`, the MCO uncordons it and starts on the second node, which goes through the same steps.

Each node is unavailable for workloads from the time it is cordoned until it is uncordoned. Workloads that run on a single replica, or that are pinned to one node, are interrupted during that window.

.Expected conditions during an upgrade
[cols="2,3,2",options="header"]
|===
| Component | Expected behavior | Resolves

| Kubernetes API server
| The `/readyz` endpoint returns HTTP `500` for several seconds each time an API server instance restarts: during the API server rollout and when each node reboots. Connections are not refused.
| Within seconds

| Web console
| Remains available.
| Not applicable

| `etcd` cluster Operator
| `Progressing=True` during etcd static pod rollouts and while a node reboots and rejoins. `Available=False` for a few seconds when a member rejoins.
| When both members run the new revision

| `PacemakerCluster` resource
| `Healthy=False` while a node is offline or rejoining. `NodeCountAsExpected=False` while the setup job removes and re-adds the node.
| When the node rejoins the Pacemaker cluster

| Other cluster Operators
| `Progressing=True` or `Degraded=True` for a short time, for example `authentication`, `console`, `openshift-apiserver`. Operators with a single replica, such as `image-registry`, report `Available=False` while their node drains.
| Within minutes

| Fencing
| Does not occur during a normal upgrade.
| Not applicable
|===
